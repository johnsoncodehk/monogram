# Highlighter evidence

How the derived highlighters (TextMate, tree-sitter, Monarch) compare with the hand-written
official ones, and where the comparison stops. The README carries the summary; this file
carries the records.

## Two questions, two measures

Two numbers answer two different questions. Read them together, not against each other.

- **Broad agreement** (the coverage table in the [README](../README.md#evidence)): over a
  whole corpus, does the derived grammar match the official **parser**'s accept/reject and
  the official **highlighter**'s token roles? This is dominated by the easy bulk of
  unambiguous tokens: the floor every grammar clears.
- **The filed bugs** (the ledger below): on the exact cases reported against the hand-written
  official grammar, does the *derived* one fix them? This strips the easy bulk away and shows
  only the ambiguous frontier: generic `<` versus less-than, regex versus division,
  whitespace-fragile multiline generics.

A near-tie in the broad table can sit next to a lopsided ledger: the broad average dilutes
the difference with easy tokens, while the ledger zooms in on the hard cases it buries.

## Reading the coverage table

- **Parser** (Monogram against the official parser, [`test/src-coverage.ts`](../test/src-coverage.ts)).
  The official parser's source is instrumented by block coverage. *agree* is the share of the
  official parser's reached branches that at least one corpus file reaches on which both
  parsers give the same verdict (accept/reject; for HTML, parse-tree equality against parse5).
  *covered* is the share of the official parser's branches the corpus reaches at all, so read
  *agree* as "on the covered portion".
- **Highlighter** (Monogram's derived TextMate grammar against the official one,
  [`test/scope-gap.ts`](../test/scope-gap.ts)): both are graded against the parser's per-token
  roles, the [vscode#203212](https://github.com/microsoft/vscode/issues/203212) comparison.
- The table is regenerated by the `readme-bench` workflow (`npm run coverage:table`) on
  pinned corpora; see [TESTING.md](TESTING.md).

The baselines are the *maintained* official grammars where they exist: JS/TS use Microsoft's
[TypeScript-TmLanguage](https://github.com/microsoft/TypeScript-TmLanguage); YAML uses
[RedCMD/YAML-Syntax-Highlighter](https://github.com/RedCMD/YAML-Syntax-Highlighter), which
VS Code switched to ([microsoft/vscode#232244](https://github.com/microsoft/vscode/pull/232244));
only HTML's baseline is the unmaintained [textmate/html.tmbundle](https://github.com/textmate/html.tmbundle),
the #203212 case Monogram targets.

## The ceiling, and the bar for claiming it

The **only-Monogram** wins above are all disambiguations that are *TextMate-expressible but
infeasible to hand-write*: a parser supplies the pattern a human can't reliably guess. The
**both-miss** cases are ones neither grammar gets *today*, not, by default, ones TextMate
*can't*.

"TextMate can't express X" is a claim to be **proven from the model**, not asserted. TextMate
is a line-oriented matcher whose only cross-line memory is a finite stack of scope contexts,
so a proof exhibits an X whose correct highlighting provably needs memory that model lacks:
unbounded lookback to a token that is not an enclosing context.

A failed *attempt* to derive a pattern is not such a proof: a cleverer pattern may exist.
Most "impossible for TextMate" folklore is exactly this error; the multiline and
nested-generic cases turn out TM-expressible once a parser supplies the pattern, which is why
the derived grammar gets them right. Where a construct provably exceeds the model, the
derived **tree-sitter** target, a real parser over the whole tree, resolves it.

## tree-sitter

The derived `queries/highlights.scm` is structural, read off the grammar's rules. Gate
`npm run gate:treesitter` ([`test/treesitter-bench.ts`](../test/treesitter-bench.ts), CI job
`treesitter`) grades token-family accuracy against a neutral `tsc` oracle over the
documented-bug corpus, and fails unless the derived grammar is at least 90% and at least the
official tree-sitter grammar. Last run (CI on `3a18a69`): Monogram 96.3%, official 92.5%.

The other derived packages are checked in the same job: every `queries/*.scm` of every
grammar must compile against its wasm ([`test/treesitter-queries.ts`](../test/treesitter-queries.ts));
the TSX and JSX grammars parse a corpus whose verdicts are compared with the interpreter's
([`test/treesitter-jsx.ts`](../test/treesitter-jsx.ts), report-only); and the job summary
records, per grammar, `tree-sitter generate` wall and CPU time, peak memory and the
`parser.c` state and symbol counts (report-only baselines for changes to the tree-sitter
generator).

A tree-sitter grammar is a CFG and has no lookahead, so the grammar's zero-width assertions
(`not`, `sameLine`, `noCommentBefore`, `noMultilineFlowBefore`, `notLeftLeaf`) are rendered
exactly only where a rewrite exists and are otherwise dropped. The generator records every
occurrence with its class ([`test/treesitter-assertions.ts`](../test/treesitter-assertions.ts),
also in the `test` job summary): `lowered` and `vacuous` are exact (FIRST/FOLLOW prove the
assertion always holds where the CFG reaches it). Every other class marks a place where the
generated grammar may accept more than the grammar does. The class names the lowering that would
make it exact: `scanner` (a line-terminator, comment or flow-state condition, for an external
scanner token), `reserved` (keywords excluded right before the word token, for a tree-sitter
`reserved` word set), `lookahead1` (a one-token lookahead over any other continuation),
`lookahead` (several tokens or a nested assertion) and `left-context` (a predicate on the left
operand). Recorded on `5a6c557`:

## Dialects and other editors

Measures of what the generators do for a grammar that is not one of the six committed ones.
They are records, not targets; each moves only with a generator change that says why.

- [`test/tm-dialect.ts`](../test/tm-dialect.ts): scope assertions on an element dialect that is
  not React ([`test/fixtures/elementdialect.ts`](../test/fixtures/elementdialect.ts): `@if` /

  tags, a `<style>` body), and on element grammars whose rule names, tag-name scope and
  conventions are not JSX's. Rows the generator does not meet yet are expected-fail with their
  reason; the gate fails when a passing row breaks and when an expected-fail row starts
  passing. Recorded on `86f6530`: dialect 6 pass / 11 expected-fail, agnostic 4 pass /
  8 expected-fail.

## Known differences from the official highlighter

A handful of token patterns are scoped differently from VS Code's official TypeScript grammar
on purpose. These are *deliberate divergences*, distinct from the bug-class fixes the ledger
measures:

| Token | Monogram | Official | Why we keep ours |
|---|---|---|---|
| `console` in `console.log` | `support.variable` | `variable.other.object` | We highlight built-in globals (`console`, `window`, …) distinctly — a deliberate, common choice. |
| `transform` (a function parameter) | `variable.parameter` | `entity.name.function` | It **is** a parameter. Official's heuristic mis-reads `name: (…) => T` as a function definition; we're more correct. |
| `error` (the method in `console.error(…)`) | `entity.name.function` | `variable.other.readwrite` | We scope a called method as a function name — arguably more informative. |

Built-in class names in **type** position (`Error` in `extends Error`) emit
`entity.name.type`, matching official; in **value** position (`new Error()`) they remain
`support.class`, also matching official.

Matching the official grammar *exactly* would, in cases like `transform`, make the output
worse. The metric counts these as differences, not defects.
